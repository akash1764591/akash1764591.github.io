four decisions behind a token compressor

S Akash · september 13, 2026 · 4 min read

a test run prints 200 passes and one failed assertion. the agent needs the failure, not the 200 green lines. where can we remove those lines without hiding the cause? RTK and Headroom answer at different points in the same trip from command to model.

1. at the shell

RTK runs in front of a shell command. its Bash hook can change git status to rtk git status before the command runs. because RTK knows the command, it can group status files, trim a diff, or collapse passing tests while keeping failures. it also preserves the exit code. a short failure remains a failure.

the hook only sees shell commands. an agent's built-in Read or Grep tool bypasses it. RTK can also cut too far: an open proposal shows a two-line git push origin main result losing the destination repository. if you needed to check where the code went, that line was the answer.

2. before the model

the agent then sends tool results and file reads to the model. Headroom's proxy or SDK works at this boundary. it compresses eligible parts of the request without dropping or reordering messages. unlike RTK, it sees the content but may not know which shell command produced it.

its ContentRouter sends logs to a filter that keeps errors and stack traces. JSON arrays go to SmartCrusher: first it tries a compact table with every item; if that saves too little, it selects items such as errors and query matches. short blocks pass through.

3. when a line is missing

even a good filter can miss what the agent needs next. RTK's recall system saves full output for failed or trimmed commands. rtk recall <hash> reads it without rerunning the command; rtk proxy <command> skips filtering up front. Headroom's Compress-Cache-Retrieve keeps the original block locally and leaves a marker. the model can use headroom_retrieve to fetch it before it expires.

Red Hat's Ripwire makes a similar trade for source code: show a map of relevant functions and locations, then expand the full code if needed. it advises skipping the map when one grep is enough.

4. on the next request

the model can cache the unchanged start of a request, including earlier messages. rewrite an old message and that match breaks. fewer tokens can still cost more if a cheap cache read becomes a new write.

Headroom's default cache mode cuts new content and leaves earlier turns alone. RTK filters command output once, before it enters the conversation. for the failed test, the agent sees the assertion now, can fetch the full log later, and keeps old messages unchanged for the next call.
