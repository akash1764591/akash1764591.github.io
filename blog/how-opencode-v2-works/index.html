how opencode's coding harness works

S Akash · september 17, 2026 · 12 min read

a coding harness builds each model request from a larger, changing session. it decides which actions to advertise, runs the ones the model selects, and records enough state to continue. OpenCode is a useful case because its source is open. the interesting questions are at the crossings: what reaches the model, what a tool can actually affect, and what happens when work is delegated or interrupted.

1. context: what is the model allowed to see?

start with three kinds of state. session state is the durable record of messages and tool results, together with related job state. working context is the subset assembled for one model step. workspace state is the actual filesystem, processes, and browser tabs. the harness has to move information among them deliberately. a conversation transcript alone cannot tell you which instructions, tools, or files were visible when a decision was made.

before each model step, OpenCode selects a view: the active part of history, instructions for this location and agent, and the tool definitions that this request may advertise. the request builder turns that view into messages and schemas for the model. the model does not read the session database or workspace directly; a later tool call is how it asks the harness to observe or change them.

instructions also have different activation points. built-in guidance and project rules can enter up front. skill descriptions advertise bodies that are loaded on demand. a successful file read can discover a nearby AGENTS.md and insert it as a later synthetic instruction. MCP server guidance is filtered against the agent's permissions and available server tools; session-level restrictions enter the separate tool snapshot, so guidance and executable availability can diverge. an input hook can alter a prompt before admission; a context hook can alter the outgoing view without rewriting stored history. a context hook may rename or describe an admitted tool, but the request builder drops invented tool definitions and maps surviving renames back to the original executable handler.

the timing is easy to miss. a rule discovered on a file read cannot have influenced an earlier edit; a skill whose description was visible is not the same as its body having been loaded. OpenCode hashes instruction sources and records changes durably, freezing the rendered update text at that point. compaction advances the instruction baseline. this gives late guidance a position in history instead of pretending every rule was present from the first turn. Anthropic’s context engineering notes make the broader case for selective context; here the selection point is part of the behavior.

2. tools: the action space is an API

OpenCode builds a tool snapshot for each request from built-in tools, plugins, and connected MCP servers. it removes wholly denied actions before advertising them. read, edit, shell, and subagent have individual model-facing schemas; other eligible operations are discoverable through a compact catalog. either way, the model sees an advertised interface, not the handler's full authority.

in OpenCode, that catalog is exposed through Code Mode: a short JavaScript program can call registered tools and return selected results, reducing tool-description and observation volume. registered calls still reach their normal handlers. the interpreter's built-in fetch is a separate HTTP capability, however, and needs its own network policy. Anthropic explains the general context-saving pattern.

the returned observation is another design choice. OpenCode normalizes tool content, runs an after hook, and caps ordinary local text at 2,000 lines or 50 KiB. when truncated, the full text goes to a temporary file with a seven-day cleanup policy. the model gets a bounded response and can retrieve more while that file exists. Cursor applies a similar file approach to long shell and MCP responses and terminal history. the mechanism matters more than the exact cap: how can the agent recover evidence left out of the current observation?

other harnesses place discovery elsewhere. Cursor keeps MCP tool descriptions in a folder per server and lets the agent search definitions as needed. Prime Agent offers a persistent Python namespace that can inspect values and call host tools across turns; that worker has OS access and is not a sandbox. these choices change how the model finds and combines operations. each still needs an answer to what the operation is allowed to affect.

3. plugins, hooks, MCP: three different boundaries

a plugin is host-side code. OpenCode activates it inside the host and gives it a context with registration APIs. the plugin can add a local tool through tool.transform, register a callback through tool.hook or session.hook, and even add an MCP server configuration through mcp.transform. these are different actions by the same plugin, not synonyms for a plugin. its setup runs in the host, so the plugin's own code needs the trust you would give other installed code.

a hook is a named point in that host's lifecycle. for example, OpenCode calls session.context while building a model request and tool.execute.before before running an admitted tool. a plugin registers the callback; the hook fires only at its particular point and receives that point's event data. callbacks run in registration order. their powers differ: tool.execute.before can reject a call, while the other hook events have no typed rejection channel. hooks are therefore control surfaces inside the host, not a protocol for talking to another service.

an MCP server is a separate capability endpoint. OpenCode talks to one over stdio or HTTP, discovers what it offers, and adapts those capabilities into the harness. an MCP tool is still subject to the host's wrapper and permission path; the server does not gain a session.context hook merely by connecting. the distinction is useful when building your own harness: use a local tool for a trusted operation tightly coupled to host state, a hook to alter a known lifecycle point, and an MCP adapter when a capability should be supplied through a separate process or service. a plugin can wire up all three.

follow one tool call. suppose an MCP server named docs advertises search. the model selects that operation and supplies a query. the host runs the tool's before hook, validates the input, and checks action docs_search with resource *. only then does the MCP adapter send the request to the server. on return it converts the response, runs the after hook, and records a result the next model step can observe.

the MCP connection itself is only transport and discovery. OpenCode connects over stdio or Streamable HTTP and maps four kinds of contribution into different host surfaces:

  • tools become callable, namespaced operations; a changed tool list refreshes the registry.
  • prompts become explicit commands that fetch server messages when invoked.
  • resources have list and read operations; connecting a server does not inject every resource into context.
  • server instructions can enter context when the server is reachable and relevant tools are permitted.

the adapter also decides what a result means to the harness: it preserves structured output, converts text and media, and parses JSON-looking text when no output schema is declared. this happens after the remote call, before the model sees the observation. server schemas and annotations describe behavior; they are untrusted hints, not the host's authorization policy. returned documents and page text remain untrusted data.

connection health is part of the harness too. OpenCode starts configured servers asynchronously, marks a connection usable after tool discovery succeeds, and updates the registry when tools change. for a tagged expired HTTP session, its recovery path reconnects and runs the original request once more. that is more than refreshing the catalog: for an effectful MCP tool, the host cannot infer from a lost response whether the first attempt acted. a missing tool, meanwhile, may mean startup, catalog drift, or authentication failure rather than a model selection error.

this adapter design leaves two separate questions. discovery: can the agent find the right capability without advertising hundreds of schemas? authority: what exactly does the host restrict? OpenCode checks the server-qualified tool name, but passes a wildcard resource to that permission check; it does not inspect the tool's arguments to authorize a particular remote object. Anthropic’s MCP code-execution essay is useful on discovery. it does not settle authority: a searchable catalog can make a dangerous operation easier to find, and a server's “read-only” annotation does not constrain what its implementation can do.

4. browser: desktop execution, server network

in this snapshot OpenCode includes an experimental browser plugin that exposes desktop Chromium to an agent when the browser pane and feature setting are active. the server owns tool definitions and RPC transfer; the desktop owns tabs, CDP, page evaluation, network capture, and screenshots. the attachment is keyed by session ID, so a child session does not inherit its parent's browser connection. page operations target an explicit tabID from that attachment's tab inventory.

the plugin provides navigation, input, accessibility snapshots with expiring element references, screenshots, and debugging records. an RPC control event carries connection and request IDs; the desktop fetches the pending command and returns a validated result. uploads cross from server-local paths as bytes into desktop-local temporary files, while captures travel back. each transfer is limited to 5 MiB because the two sides cannot assume a shared filesystem.

oh-my-pi instead exposes a browser facade inside its Eval tool, so one script can observe, act, and extract before returning a compact answer. Cursor’s cloud agent describes a specialist computer-use subagent with its own prompt and screen recording, sharing the browser with its parent.

the boundary is still unfinished in OpenCode's base plugin: its README explicitly leaves per-URL and server-file permission checks for a later layer. Chromium and page JavaScript run on the desktop, but page traffic goes through a TCP tunnel to the connected server's network, including its loopback and LAN. a URL check only on the model's initial navigation argument would miss subsequent requests induced by the page. after a timeout, a click or upload may already have happened, so repeating it blindly risks a second side effect. page content, headers, and logs remain untrusted even when the RPC result validates.

agent-browser packages browser actions as CLI commands and snapshots with element references; Playwright MCP supplies browser actions through MCP tools and structured accessibility snapshots. the packaging changes how actions are discovered and observations enter context; URL and network authority still need their own policy.

5. execution control: policy, location, hooks

advertising a tool does not authorize the call. OpenCode can hide wholly denied tools from the registry snapshot, then evaluate action and resource at a handler through ordered permission rules; the last matching rule wins, unmatched requests ask, and a saved approval cannot override an explicit denial. file tools check paths; the MCP wrapper checks a server-qualified action; the shell tool scans resources and validates the working directory. custom plugins must supply the checks their effects require. the browser gap above shows why “the registry has permissions” is not a complete security claim.

location matters independently. a session environment binds filesystem operations and process spawning. the local driver uses host filesystem and process APIs when no workspace driver is selected; the workspace registry has no isolated provider by default. permission answers “may this action run?”; the driver answers “where can it affect state?” Codex makes that distinction concrete by combining approval decisions with a sandbox that enforces filesystem and network limits. Devin starts sessions from a prepared organization environment snapshot, which addresses reproducibility of tools and dependencies. a clean starting environment and an enforced runtime boundary solve different problems.

hooks provide another seam: tool.execute.before may change input or reject the call, and tool.execute.after may change the result. for a top-level call, OpenCode resolves a hook-changed tool name against the definitions admitted for that request, then the handler checks its relevant resource. as the provider streams tool-call events, the step executor can start independent local calls in parallel. it waits for them all to settle after the stream ends, then builds the next model step.

Claude Code puts PreToolUse before its permission evaluation; a hook can block a call, while permission policy still has the final say on a denial. Pi extensions can register tools, intercept tool_call, and customize context or compaction from one extension API. they run with the user's OS permissions, so extension flexibility is not isolation.

hook order matters because the arguments checked by policy should be the arguments the handler executes. the OpenCode registry, handler checks, and environment driver each cover a different part of that path. none can stand in for the others: a prompt-visible restriction does not constrain a process, and an approval dialog does not prove where its effects landed.

6. subagents: a new context with a return path

OpenCode advertises eligible child agents by name and description in the subagent tool description. the model chooses whether to call subagent; no separate task classifier fires in this path. the handler checks the selected agent, permission, and depth (one level by default), then starts a child session with its own agent choice and task prompt. the child's message history is separate from the parent's. a later call can pass its sessionID to continue that child; the handler verifies that the session belongs to the current parent, so the ID is not a way to attach an arbitrary conversation.

foreground delegation waits for final child text. background delegation returns a session ID, and completion delivery later inserts a synthetic notice for the parent. configured commands can also launch a background child; that route creates the session directly and does not pass through the subagent tool's depth and agent-specific permission gate. the child uses the parent's working location by default, so separate context does not imply separate files.

Claude Code can give a child its own Git worktree. oh-my-pi offers batched tasks with bounded concurrency and optional isolated spawns that merge by patch or branch. those are decisions about file conflicts and return artifacts, not simply how many agents to run.

the return contract matters as much as the trigger. a child summary can answer a research question, but it cannot by itself reconcile two concurrent edits to the same file. for implementation work, the harness needs an ownership or merge strategy; separate transcripts alone do not provide one. tasks too small to split also pay the startup and coordination cost without gaining useful parallelism.

7. persistence: what survives the next step or a crash?

an incoming prompt is first recorded in the session inbox; a queued message waits for current work to drain, while a steer can be delivered at a safe step boundary. delivered messages, settled tool calls, and job outcomes become session state. OpenCode's event bus projects durable session events into SQLite views as they are published. full payload retention for cursor replay is optional and off in the normal CLI server configuration; live token fragments seen by a UI are not necessarily a token-by-token durable log.

the history builder does not send every stored turn forever. when context grows, local compaction records a new checkpoint: a summary of older work followed by a serialized recent tail. later requests can start from that checkpoint while the original turns remain stored. the tail targets about 15,000 tokens; tool text in it is clipped to 2,000 characters and attachments become descriptions. the automatic trigger reserves at least a 20,000-token buffer. this is a deliberately lossy working view, not a deletion of the transcript.

a provider-native checkpoint is different: it is an opaque replacement window, not a summary another model can read. OpenCode replays it only when provider, model, route, and endpoint match its recorded provenance. otherwise the history builder skips that checkpoint and rebuilds the request from eligible original messages. a request hook cannot retarget a selected native window to another endpoint. the session record can be unchanged while the working context takes a different shape.

recovery is weaker than exactly-once execution. after a managed restart, the restart path can resume an unreleased execution claim with a notice and a bounded attempt count. it describes this as at-least-once: a crash between an external commit and the local success record leaves the outcome uncertain. local coordination prevents two active drains, but cannot undo or deduplicate that remote action. an effectful tool needs a durable call ID that the remote system accepts as an idempotency key, or a way to query and reconcile the previous attempt before retrying.

other harnesses preserve different things. Pi records a branchable JSONL session tree, letting a user return to an earlier point in the conversation; that branch does not roll the filesystem back. Prime Agent’s daemon adapter reconnects clients using event cursors and snapshots. its protocol journals mutating commands by client and command ID: a completed duplicate returns the recorded result, while a command received without a durable result is reported as uncertain rather than replayed. Pi makes conversational branching explicit; Prime Agent makes client reconnection and duplicate commands explicit. neither contract, by itself, undoes an external side effect.

the boundaries that matter most

the recurring difficulty is that each part knows something different. the registry knows which operations to describe; the handler knows which path, command, or remote object a call will touch. a child session has separate messages but may share files. the session log knows what was recorded, while a remote service knows what actually committed. when building a harness, the contracts between those parts need to say where authority is checked, where effects land, what returns to the model, and what can be retried after a failure.
